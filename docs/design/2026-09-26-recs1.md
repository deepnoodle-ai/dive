## Summary

The difficult part is agreeing on **when execution is allowed to advance**.
Dive knows the model/tool loop; nvoken owns durable authority, accounting, and
recovery. The adapter currently reconstructs that agreement through message
callbacks, model wrappers, tool wrappers, and sentinel errors. A complete step
protocol would remove much of this reconstruction while preserving nvoken's
Postgres authority. Evidence: `Generator.generate` in
`internal/adapters/divegen/generator.go`, `ToolCheckpointService` in
`internal/services/toolcalls.go`, and `loadGenerationRecovery` in
`internal/services/generation_recovery.go`.

The strongest existing foundation is the checkpoint transaction: assistant
message, tool intents, callback deliveries, private replay artifacts, model-call
settlement, and checkpoint advance belong to one fenced transaction. Recovery
validates stored relationships and can finish an already committed final
response without calling the model again. These are service guarantees worth
keeping. Evidence: `RecordModelCheckpoint`, `CommitModelCheckpoint` in
`internal/adapters/postgres/toolcalls.go`, and
`TestGenerationExecutorSettlesCommittedFinalCheckpointWithoutProviderCall`.

The concrete correctness issue is **ORCH-03**: a tool's persistence error can
become model-visible tool feedback instead of stopping execution. The most
valuable upstream changes are **DIVE-01/04** (complete acknowledged steps),
**DIVE-05/06** (typed execution control), **DIVE-11/12/13** (call lifecycle and
provider errors), and **DIVE-15** (replay codecs).

Version matters. Dive v1.34 already adds incomplete outcomes, partial-response
preservation, step checkpoints, and claims. These should not be requested as
if they did not exist. Its step persistence is still reached through a
`TurnStore` session. The newer `experimental/v2` prototype directly explores
application-owned recording, but supports text and one tool call per model
result and is explicitly unsupported. Evidence: Dive `durability.go`,
`outcome.go`, `experimental/v2/{README.md,engine.go}`, and the
[v1.34 release](https://github.com/deepnoodle-ai/dive/releases/tag/v1.34.0).

## What nvoken built around Dive

| Boundary | Implemented abstraction | Why nvoken needs it |
| --- | --- | --- |
| Execution ownership | `ExecutionClaim`, lease owner plus attempt; `ClaimExecutor` | A restarted or stale worker must not commit over its successor. |
| Before a paid call | `resolvingModel`, `ModelCallAuthority` | Resolve current credential authorization, reserve credit, record a call fact, and fence call admission. |
| After a model response | `ModelCheckpointInput`, `RecordModelCheckpoint` | Persist response, usage, tool intents, deliveries, and replay state before tools run. |
| Tool execution | `DurableToolCoordinator`, builtin/MCP wrappers | Record start/result under the claim; distinguish external waiting from inline execution. |
| Restart | `GenerationResume`, `loadGenerationRecovery` | Rebuild the loop from committed transcript/checkpoint/tool evidence. |
| Provider continuity | `ProviderMessageArtifact`, split/rehydration helpers | Retain signatures and provider metadata without exposing them as public transcript data. |
| Live output | normalized deltas and reserved message IDs | Allow previews to disappear without making them authoritative history. |

## Why this is hard

**There is no transaction spanning Postgres and a provider or remote tool.**
The process can die after an effect occurs but before its result commits. A
lease fence rejects stale database writes; it cannot undo an HTTP request.
nvoken records model facts as `prepared`, `started`, `settled`, `not_started`,
or `uncertain`; cleanup resolves abandoned facts instead of treating missing
usage as zero. MCP restart distinguishes retry-safe calls from calls whose
effects are uncertain. A library can represent uncertainty and stable identity;
exactly-once remote effects still require idempotency or reconciliation at the
external system. Evidence: `model_call_facts` in
`internal/adapters/postgres/schema.sql`, `resolveOpenModelCallFacts`,
`StartMCPToolCall`, and `safeMCPRetry`.

**There are several different meanings of failure.** Invalid tool arguments
can be fed back to the model. A provider 429 may justify a bounded retry. A
failed checkpoint requires reload/recovery. Lease loss requires the current
worker to stop. A budget hold or host-tool wait is a state transition. Combining
these into ordinary Go errors forces both adapters and services to rebuild the
distinction. Evidence: `ProviderCallError`, `TransientFailure`,
`errCheckpointBudget`, `errCheckpointInterrupt`, `Generator.generate`, and
`GenerationExecutor.Execute`.

**Readable history is not sufficient replay state.** Reasoning signatures,
provider-owned tool blocks, metadata, tool identities, and call ordering must
survive. Reusing them across incompatible model/reasoning lineage is unsafe.
nvoken separately preserves public content and private artifacts and validates
their association and digest before reattachment. Evidence:
`fromDiveMessage`, `providerArtifactsWithRewrittenToolIDs`,
`rehydrateStoredMessagesForGeneration`, and `validateProviderMessageArtifact`.

**A live stream is evidence of observation, not commitment.** In v1.31 the
adapter emits previews before the full message checkpoint. A partial stream
can disappear on failure while a model call remains financially uncertain.
Provider-tool Turns deliberately use blocking generation because the pinned
stream accumulator discards provider-owned blocks. Evidence:
`normalizedDelta`, `budgetStreamIterator`, `nonStreamingModel`, and
`TestGeneratorUsesLosslessNonStreamingResponseForProviderTools`; Dive v1.31
`llm/stream.go` (`ResponseAccumulator.AddEvent`).

## ORCH-03 / DIVE-06: stop on infrastructure failure inside a tool

**Priority: correctness first. Confirmed in this worktree.**

Builtin and MCP tools return coordinator failures as ordinary Go errors. Dive
v1.31 `Agent.executeTool` converts these to `ToolResult.IsError`, preserving
the error as text for the next model call. nvoken installs no corresponding
`PostToolUseFailure` abort hook. Its tool-result event callback settles unknown
tool names; it does not stop this ordinary declared-tool failure path.
Evidence: `deterministicEchoTool.Call`, `Generator.generate`,
`settleUnknownToolCall`, and `mcpTool.Call`.

The probe replaced only `AcceptBuiltinToolResult` with a coordinator returning
`ports.ErrRetryable`, leaving the real generator and Dive loop intact. The
scripted model requested a builtin and then answered. Observed: **two model
calls and a nil generator error**, despite the rejected tool-result write.
This reproduces continuation, not actual provider charges or duplicate effects.

The claim fence does narrow the risk: after real lease loss,
`ModelCallAuthority.PrepareModelCall` can refuse the next call, and heartbeat
cancellation also stops work. It does not solve a transient result-write
failure while the lease is still valid. Therefore the finding is not that
stale workers universally bypass fencing; it is that persistence failures are
misinterpreted as recoverable tool-domain feedback.

Near-term nvoken fix: bridge durable tool infrastructure errors into
`HookAbortError` through `PostToolUseFailure`, preserving their wrapped cause.
Test both start and accept failures, lease loss, and a mixed tool batch.
Upstream: distinguish tool-domain failure, engine abort, suspension, and
uncertain external execution in the tool contract. Error text must not decide
whether another paid call is permitted.

## DIVE-01 / DIVE-04: complete steps acknowledged by the caller

Today nvoken's message callback reconstructs iteration, served model, usage,
fact identity, preview identity, requested tools, and checkpoint control.
`ResponseItemTypeMessage` does not supply a complete model-call record;
`fromDiveMessage` rejects empty content even though a real call can consume
tokens without yielding public text. The wrappers and local state compensate
for this. Evidence: Dive v1.31 `response.go`, and nvoken
`generationCheckpointState`, `modelEvidence`, `Generator.generate`.

The useful upstream abstraction is a storage-neutral synchronous recorder.
Each step needs a version, stable turn/call/step identity, observed result,
usage knowledge, stop reason, and tool disposition. The recorder may atomically
write that step together with application-owned facts. No next model call or
tool effect follows until recording is acknowledged. A rejected write and an
unknown commit outcome must be distinct; an unknown outcome requires reload
and idempotent reconciliation.

Conceptual ownership, not a proposed new service layer:

```text
Dive engine -> complete step -> nvoken recorder -> fenced Postgres transaction
     ^                              |
     +------ acknowledgement -------+

Dive session runner -> the same engine and recorder contract
```

Keep Dive sessions as a convenience consumer. nvoken should not need a second
session authority to obtain the engine's step guarantees. v1.34 `TurnStore`
and `DurabilityOptions` partially address the problem; the v2 prototype's
`Recorder.Commit`, `CommitError`, stable `EffectID`, and unacknowledged result
are promising concrete evidence of the direction. Its scripted process test
does not qualify Postgres durability or the full provider/tool matrix.

## DIVE-05 / DIVE-11: explicit control and model-call lifecycle

`resolvingModel` recreates providers per call so credentials can be revoked
between iterations. It estimates the assembled request, reserves credit, and
marks call start. Iterator wrappers collect output timing and uncertain
completion. Budget and interrupt decisions escape the loop as sentinel errors.
Evidence: `resolve`, `reserve`, `consume`, `budgetStreamIterator`, and
`checkpointBudgetExceeded` in `generator.go`.

Dive should expose one call lifecycle for blocking and streaming execution:
prepare the effective request, authorize/refuse it, record the attempt, observe
completion or uncertainty, and report a typed continuation/stop decision.
Include requested/served model, retry ordinal, stable request identity where
available, known versus unknown usage, and partial output separately from a
committed response. Allow caller-owned credentials and admission decisions
without reconstructing provider configuration around every call.

nvoken explicitly disables Dive retries (`providerRetriesDisabled = 0`).
`GenerationExecutor.Execute` settles provider failures, while retryable
infrastructure failures escape for lease recovery. These are different forms
of resilience: **durable recovery does not currently imply provider retries**.
PRD 054 remains proposed; its old description of hidden retries is superseded
by the explicit constructor settings and `TestProviderConstructionDisablesDiveRetries`.
A retry contract must expose and authorize every attempt, retain uncertain
spend, obey deadlines, and prevent automatic stream replay after output has
escaped. Retryability alone is not proof that an effect did not occur.

## DIVE-12 / DIVE-13: normalize provider failures at their source

nvoken intercepts HTTP 400 bodies, bounds their size, matches vendor-specific
context/media errors, then discards unsafe prose. `providerErrorType` even
extracts JSON from `err.Error()`. Google's constructor lacks the injectable
client needed for that inspection; xAI is reconstructed with the OpenAI
provider to obtain it. Evidence: `context_window.go`, `media_rejection.go`,
`classifiedProviderCallError`, `newGoogleModel`, and `newXAIModel`.

Dive already has `providers.ProviderError` with status, code, and retry-after;
extend it with normalized failure categories and typed bounded evidence for
context overflow, media rejection, refusal, and response validity. Preserve
private diagnostic details separately. Give every provider equivalent explicit
client/endpoint/credential construction. nvoken should retain its public error
mapping and redaction policy, but delete its provider-body inspection machinery
once equivalent coverage is qualified.

## DIVE-15 / DIVE-10 / DIVE-14: replay, stream parity, and capabilities

A versioned message codec should preserve replay-critical provider extensions,
offer a conservative public/private projection, and describe compatibility
when model or reasoning settings change. nvoken still owns artifact storage,
tenant isolation, integrity, erasure, and the public transcript allowlist.
Evidence: `ProviderArtifactDialectDiveV1`, `fromDiveMessage`, and
`internal/services/provider_artifacts.go`.

Streaming and blocking should produce equivalent durable content, usage, and
stop evidence. Newer Dive reconstructs server-tool blocks that v1.31 skips,
but the inspected v1.34/current accumulator still has no citation-delta case.
Do not remove nvoken's non-streaming safeguard merely on a version bump;
qualify each supported provider-tool transcript and its replay. Evidence:
Dive `llm/stream.go` and nvoken's provider-tool preservation test above.

Export provider/model capability and strict validation data so nvoken does not
re-encode reasoning/tool-choice/media combinations. nvoken keeps its qualified
offering and admission policy. This extends the older `PROV-02` concern;
it does not mean every Dive model should be offered. Evidence:
`model_catalog.go`, `validateGenerationReasoning`,
`validateGenerationToolChoice`, `validateGenerationInputMedia`, and
`TestAnthropicToolChoiceCatalogMatchesDive`.

## Suggested order and proof

1. Fix **ORCH-03** in nvoken and retain fault-injection coverage proving no
   subsequent model call after an uncommitted tool result.
2. Qualify a Dive upgrade as a behavior change (**DIVE-17**): v1.34 adds nil-error
   incomplete outcomes, which this adapter does not explicitly map. The primary
   checkout's upgrade review is relevant evidence, not proof for this worktree.
3. Advance **DIVE-01/04/05/06** using the existing v2 prototype: acknowledge
   model/tool steps, distinguish uncertainty, and test restart at each boundary.
4. Add **DIVE-11/12/13**, then remove wrappers and inspectors only when their
   accounting, credential, and error tests pass against the replacements.
5. Deliver **DIVE-15/10/14** with persisted fixtures and cross-provider replay
   tests. This is integration maintenance work grounded in existing workarounds;
   broader capability expansion remains a separate product decision.

The decisive protocol tests are: rejection before an effect; lost acknowledgement
after a commit; restart after remote effect but before result commit; stale-owner
write; duplicate result delivery; partial stream with unknown usage; and mixed
tool batches. Passing those is more meaningful than a smaller `generator.go`.
The v2 prototype already exercises several of these with scripted storage and
effects; production storage and provider qualification remain additional work.
