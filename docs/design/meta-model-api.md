# Meta Model API (Muse Spark)

_Last updated: 2026-09-02_
_Status: prototype built and merged into the working tree; unverified against a
live key. The provider compiles, is registered, is wired into the CLI, and passes
its tests. No generation request has been made — see
[Verification status](#verification-status)._

Support for Meta's Model API, launched 2026-09-02, serving the **Muse Spark**
family (`muse-spark-1.3` and siblings) at `https://api.meta.ai/v1`.

Sources: [models](https://dev.meta.ai/docs/models),
[protocols](https://dev.meta.ai/docs/protocols),
[reasoning](https://dev.meta.ai/docs/reasoning),
[pricing and rate limits](https://dev.meta.ai/docs/pricing-rate-limits),
[prompt caching](https://dev.meta.ai/docs/prompt-caching).

## Summary

Meta serves one set of models over three wire formats — Responses, Chat
Completions, and Messages — all at the same price, on the same auth. Dive already
has a mature client for two of the three, so the integration is small. The whole
design question is *which format*, and the docs answer it unambiguously for an
agent framework:

> Chat Completions cannot carry reasoning across turns for external API keys.
> Assistant messages expose a `reasoning_content` field, but it holds the model's
> **private** chain of thought and is **redacted to empty** before the response
> reaches an external caller [...] each turn reasons from scratch.
> — [Reasoning § Multi-turn](https://dev.meta.ai/docs/reasoning#multi-turn)

Muse Spark is a reasoning model marketed for "long-horizon, agentic workflows" —
multi-step tool loops are the whole point. Routing it through Chat Completions
would throw away the reasoning at every tool-result boundary, which is exactly
where an agent loop spends its turns. **So Dive targets the Responses API**, and
the provider becomes a thin wrapper over `providers/openai`, the same shape as
`providers/grok`.

That choice is what makes this cheap. `providers/openai` already implements
stateless encrypted-reasoning replay: it sets `include:
["reasoning.encrypted_content"]`, decodes the returned `encrypted_content` into
`llm.ThinkingContent.Signature` (`decode.go:314`), and re-encodes it as a
reasoning input item on the next turn (`encode.go:591`). That is precisely the
mechanism Meta documents for stateless replay, and it needs no new code.

## What was built

A new module, `providers/meta` (package `meta`), ~120 lines of hand-written Go
plus a catalog:

| File | Purpose |
| --- | --- |
| `meta.go` | `Provider` embedding `openaiProvider.Provider`, pointed at `https://api.meta.ai/v1` |
| `options.go` | `config` + `With*` options, mirroring Grok's surface |
| `register.go` | Registry entry: name `meta`, `PrefixMatcher("muse-")` |
| `catalog.json` | The five Muse Spark ids, context windows, and both pricing tiers |
| `*_gen.go` | Generated by `scripts/generate_provider_catalogs.py` |
| `pricing_register.go` | Publishes pricing so `llm.PopulateCost` attaches spend |
| `meta_test.go` | Routing, pricing, capability-drift, and effort-clamping tests |

Plus, outside the module:

- **`providers/modelcaps`**: a `museTable` and a `TableFor` case. Muse Spark's
  effort ladder is closed at both ends — `"none"` returns **HTTP 400** rather
  than being ignored, and `"max"` is not offered — so the ladder runs `minimal`
  through `xhigh`. Without a table entry, a portable `ModelSettings` carrying
  `none` would break every request.
- **`scripts/generate_provider_catalogs.py`**: a `meta` target.
- **`experimental/cmd/dive`**: blank import, catalog registration, a `Meta` entry
  in the provider picker, and a `getDefaultModel` branch.

### Model and price table

Every Muse Spark version shares a 1,048,576-token context window and the same
modalities; they differ only in capability and tier.

| Model | Tier | Input | Cached | Output |
| --- | --- | --- | --- | --- |
| `muse-spark-1.3` | Standard | $1.25 | $0.15 | $4.25 |
| `muse-spark-1.3-contributor` | Contributor | $0.10 | $0.002 | $0.20 |
| `muse-spark-1.2` | Standard | $1.25 | $0.15 | $4.25 |
| `muse-spark-1.2-contributor` | Contributor | $0.10 | $0.002 | $0.20 |
| `muse-spark-1.1` | Standard | $1.25 | $0.15 | $4.25 |

There is no long-context premium — one rate at any context length, unlike Grok
and Google — so no `long_context_*` fields appear in the catalog.

## Decisions worth stating

**The `-contributor` tier is catalogued but not recommended.** It is 12.5x
cheaper on input and 21x on output because Meta trains on your prompts and
completions. That is a legitimate trade for prototyping and Meta sells it as
one, but it is not a thing to pick blind from a model menu, so it carries no
`recommended` flag and no `cli_order`. It stays reachable by explicit id. Anyone
routing production traffic to it should be doing so on purpose.

**Matching on `muse-`, not on the vendor.** `meta-llama/llama-3-70b` is an
OpenRouter id for Meta's open-weight models, which Model API does not serve.
Matching the model family rather than the vendor name keeps those ids falling
through to OpenRouter's `ContainsMatcher("/")`, where they belong. A test pins
this.

**API key: `MODEL_API_KEY`, then `META_API_KEY`.** Meta's docs and SDK samples
use `MODEL_API_KEY`. It is a strikingly generic name for a process that holds
keys for several vendors, so the provider accepts a namespaced alias, and the
CLI's `getDefaultModel` checks Meta **last** — a collision on a name that
generic should not silently redirect an existing setup.

## What was deliberately left out

- **Muse Image** (`muse-image-1.0`, $0.01/image) and **Muse Voice Transcribe**
  (`muse-voice-transcribe-1.0`, $0.18/hour). Different modalities needing their
  own plumbing — image generation and a WebSocket ASR endpoint. Dive has
  precedent for both (`cmd_image.go`, Google's transcribe models), so these are
  follow-ups, not blockers.
- **Muse Glimmer**, the open-weight model. Self-hosted, served through vLLM or
  llama.cpp, so it reaches Dive through the Ollama / OpenAI-compatible path
  already, not through this provider.
- **Server-side tools**: `web_search` grounding ($2.50 per 1,000 queries) and
  tool search. Grok's `tool_web_search.go` is the template when wanted.
- **`previous_response_id` chaining.** Dive's session model is stateless replay,
  and `llm.Config.PreviousResponseID` already exists for callers who want the
  server-managed form.
- **The Messages-format endpoint.** `POST /v1/messages` would let Dive's
  Anthropic provider talk to Muse Spark, which is a curiosity rather than a need
  given Responses is the richer surface.

## Open questions and risks

1. **The docs are one day old and visibly still in edit.** The published pricing
   page carries an unresolved editorial note — "Confirm these rate-limit numbers
   against the launch configuration before publishing. They are present in the
   current mdoc draft but are not specified in Part A of the positioning SoT."
   Prices and rate limits should be re-checked before this ships in a release.

2. **No reasoning effort means no reasoning replay.** `providers/openai` sets
   `include: ["reasoning.encrypted_content"]` only inside the branch that sends a
   reasoning parameter (`provider.go:276`). A caller who leaves
   `ReasoningEffort` unset gets a model that still reasons — Meta reasons at a
   model-determined level when the field is omitted — but Dive never asks for the
   encrypted content, so nothing replays across tool turns. This is pre-existing
   behavior affecting OpenAI and Grok equally, but it matters more here, because
   reasoning continuity is the entire reason this provider is on Responses.
   Worth deciding: either always request the include, or document that agentic
   use should set an effort.

3. **Effort ladder is from documentation, not probe.** Every other entry in
   `modelcaps` was verified by sending the parameter to the live endpoint and
   recording 200 vs 400 — that is the package's stated contract. The Muse entries
   are read from Meta's docs. They should be probed before release, and the
   `minimal` end is the one to check first.

4. **`max_tokens` covers reasoning plus visible output.** The default of 32,768
   is inherited from Grok. On a model that can spend heavily on reasoning at
   `xhigh`, that may truncate visible answers. Worth a look once there is a key.

5. **1M context vs. Dive's compaction defaults.** Nothing breaks, but the
   thresholds in `experimental/compaction` were tuned for 200K-class models.

`WithReasoningEffort` set and confirm that `encrypted_content` survives the
round trip.
