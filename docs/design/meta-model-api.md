# Meta Model API (Muse Spark)

_Last updated: 2026-09-02_
_Status: built and verified against the live API with a real key. Generation,
streaming, tool calling, encrypted-reasoning replay, the full reasoning-effort
ladder, search grounding, image generation and editing, and speech to text were
all exercised end to end — see [Verification status](#verification-status)._

Support for Meta's Model API, launched 2026-09-02, serving the **Muse Spark**
family (`muse-spark-1.3` and siblings) at `https://api.meta.ai/v1`.

Sources: [models](https://dev.meta.ai/docs/models),
[protocols](https://dev.meta.ai/docs/protocols),
[reasoning](https://dev.meta.ai/docs/reasoning),
[pricing and rate limits](https://dev.meta.ai/docs/pricing-rate-limits),
[prompt caching](https://dev.meta.ai/docs/prompt-caching).

## Summary

Meta serves one set of models over three wire formats — Responses, Chat
Completions, and Messages — all at the same price, on the same auth. Dive already
has a mature client for two of the three, so the integration is small. The whole
design question is *which format*, and the docs answer it unambiguously for an
agent framework:

> Chat Completions cannot carry reasoning across turns for external API keys.
> Assistant messages expose a `reasoning_content` field, but it holds the model's
> **private** chain of thought and is **redacted to empty** before the response
> reaches an external caller [...] each turn reasons from scratch.
> — [Reasoning § Multi-turn](https://dev.meta.ai/docs/reasoning#multi-turn)

Muse Spark is a reasoning model marketed for "long-horizon, agentic workflows" —
multi-step tool loops are the whole point. Routing it through Chat Completions
would throw away the reasoning at every tool-result boundary, which is exactly
where an agent loop spends its turns. **So Dive targets the Responses API**, and
the provider becomes a thin wrapper over `providers/openai`, the same shape as
`providers/grok`.

That choice is what makes this cheap. `providers/openai` already implements
stateless encrypted-reasoning replay: it sets `include:
["reasoning.encrypted_content"]`, decodes the returned `encrypted_content` into
`llm.ThinkingContent.Signature` (`decode.go:314`), and re-encodes it as a
reasoning input item on the next turn (`encode.go:591`). That is precisely the
mechanism Meta documents for stateless replay, and it needs no new code.

## What was built

A new module, `providers/meta` (package `meta`), ~120 lines of hand-written Go
plus a catalog:

| File | Purpose |
| --- | --- |
| `meta.go` | `Provider` embedding `openaiProvider.Provider`, pointed at `https://api.meta.ai/v1` |
| `options.go` | `config` + `With*` options, mirroring Grok's surface |
| `register.go` | Registry entry: name `meta`, `PrefixMatcher("muse-")` |
| `catalog.json` | The five Muse Spark ids, context windows, and both pricing tiers |
| `*_gen.go` | Generated by `scripts/generate_provider_catalogs.py` |
| `pricing_register.go` | Publishes pricing so `llm.PopulateCost` attaches spend |
| `tool_web_search.go` | Search grounding as a server-side tool, Meta's option set only |
| `media.go` | Muse Image generation and editing |
| `transcribe.go` | Muse Voice Transcribe over `POST /v1/asr/transcribe` |
| `media_register.go` | Media registry entries for the image and transcription models |
| `meta_test.go` | Routing, pricing, capability-drift, and effort-clamping tests |

Plus, outside the module:

- **`providers/modelcaps`**: a `museTable` and a `TableFor` case. Muse Spark's
  effort ladder is closed at both ends — `"none"` returns **HTTP 400** rather
  than being ignored, and `"max"` is not offered — so the ladder runs `minimal`
  through `xhigh`. Without a table entry, a portable `ModelSettings` carrying
  `none` would break every request.
- **`providers/openai`**: two fixes that this provider made visible but that
  apply to every Responses provider — requesting the encrypted-reasoning include
  whenever the model reasons rather than only when an effort is named, and
  keeping what a `web_search_call` actually did and found instead of decoding it
  down to a bare ID. See [Fixes upstream of this provider](#fixes-upstream-of-this-provider).
- **`scripts/generate_provider_catalogs.py`**: a `meta` target.
- **`scripts/provider_watch.py`** and its baseline: Meta joins the weekly catalog
  and pricing drift watch. Without the `PROVIDERS` entry the watcher would never
  have looked at Meta at all, and without a baseline its first run would have
  reported every Meta page as new.
- **`scripts/sync_module_versions.py`**: `providers/meta` in `SUB_MODULES`, so
  the release process rewrites its `dive` requirement. A sub-module tagged while
  requiring an older core release fails to build for everyone downstream.
- **`experimental/cmd/dive`**: blank import, catalog registration, a `Meta` entry
  in the provider picker, `getDefaultModel` and `getDefaultImageModel` branches,
  and a compaction threshold that scales to the model's context window
  ([below](#compaction-and-the-1m-window)).

### Model and price table

Every Muse Spark version shares a 1,048,576-token context window and the same
modalities; they differ only in capability and tier.

| Model | Tier | Input | Cached | Output |
| --- | --- | --- | --- | --- |
| `muse-spark-1.3` | Standard | $1.25 | $0.15 | $4.25 |
| `muse-spark-1.3-contributor` | Contributor | $0.10 | $0.002 | $0.20 |
| `muse-spark-1.2` | Standard | $1.25 | $0.15 | $4.25 |
| `muse-spark-1.2-contributor` | Contributor | $0.10 | $0.002 | $0.20 |
| `muse-spark-1.1` | Standard | $1.25 | $0.15 | $4.25 |

There is no long-context premium — one rate at any context length, unlike Grok
and Google — so no `long_context_*` fields appear in the catalog.

`muse-image-1.0` is catalogued at $0.01 per image. `muse-voice-transcribe-1.0`
is catalogued without a price: it is billed at $0.18 per hour of audio processed
and `modelcatalog.Pricing` has categories for text, image, and embeddings only.
Recording per-hour audio pricing needs a schema change, which is a larger change
than this provider should make on its own.

## Decisions worth stating

**The `-contributor` tier is catalogued but not recommended.** It is 12.5x
cheaper on input and 21x on output because Meta trains on your prompts and
completions. That is a legitimate trade for prototyping and Meta sells it as
one, but it is not a thing to pick blind from a model menu, so it carries no
`recommended` flag and no `cli_order`. It stays reachable by explicit id. Anyone
routing production traffic to it should be doing so on purpose.

**Matching on `muse-`, not on the vendor.** `meta-llama/llama-3-70b` is an
OpenRouter id for Meta's open-weight models, which Model API does not serve.
Matching the model family rather than the vendor name keeps those ids falling
through to OpenRouter's `ContainsMatcher("/")`, where they belong. A test pins
this.

**API key: `MODEL_API_KEY`, then `META_API_KEY`.** Meta's docs and SDK samples
use `MODEL_API_KEY`. It is a strikingly generic name for a process that holds
keys for several vendors, so the provider accepts a namespaced alias, and the
CLI's `getDefaultModel` checks Meta **last** — a collision on a name that
generic should not silently redirect an existing setup.

## Search grounding

`NewWebSearchTool` is a server-side tool in the shape of Grok's, with one
deliberate difference: **no domain allow/deny list**. Meta does not document
one, and on this API an unsupported field is a 400 rather than something the
server ignores, so the option set is limited to what Meta documents —
`SearchContextSize`, `UserLocation`, and `IncludeResults`.

`IncludeResults` asks for `include: ["web_search_call.results"]`, which returns
the title, URL, and snippet of every hit the model saw. Meta's own docs
recommend checking those when an answer matters, because coverage is incomplete;
the `url_citation` annotations are only the subset the model actually cited.

Muse Spark narrates before it searches — a first message saying "I'll search
for …", then the search, then the answer in a second message. Two consequences
worth knowing: the answer is not the whole of the output text, and a token
budget that runs out mid-search leaves only the narration behind.

## Compaction and the 1M window

The CLI compacted at a flat 100000 tokens, which was half a window when every
model it ran had 200K. On Muse Spark's 1M that discards nine tenths of the
context the model was chosen for, so the default is now half the model's
*usable* window.

"Usable" is load-bearing. The catalog lists 1M for the current Claude models
too, but that tier is behind the `context-1m-2025-08-07` beta header and the
CLI builds Anthropic models through the plain registry, which never sends it.
Deriving from the catalog number there would put the threshold past the size the
API rejects outright, so compaction would never run at all. Claude is capped at
its ungated 200K and lands on the same 100000 as before.

## Fixes upstream of this provider

Two defects in `providers/openai` that this work surfaced. Both affect OpenAI
and Grok identically; neither was introduced here.

**The encrypted-reasoning include was gated on naming an effort.** The include
was requested only inside the branch that sends a reasoning parameter, so a
caller who left `ReasoningEffort` unset got a model that still reasons — Meta
reasons at a model-determined level when the field is omitted — with nothing
carried across tool turns. It is now requested whenever `modelcaps` says the
model reasons, which is the case for every Muse Spark id. Reasoning continuity
is the entire reason this provider is on Responses, so leaving it to a caller's
optional field was not a defensible default.

**A `web_search_call` decoded to nothing but its ID.** The query, the page
opened, and the retrieved hits were all dropped, which made `IncludeResults` —
and OpenAI's identical include — pay for data no caller could read. Replaying
the call into a later turn also sent an empty query, so the history recorded
that a search happened without recording what it asked. The action now lands in
`ServerToolUseContent.Input` and the query is replayed; the hits are read out of
the raw payload, since the SDK models no field for the `results` array Meta and
OpenAI both return.

## Beyond text generation

**Muse Image** (`muse-image-1.0`, $0.01/image) is a `media.ImageProvider` and
`media.ImageEditor`, reachable through `media.GenerateImage` and
`media.EditImage` like any other model, and through the media registry that
`dive image -m muse-image-1.0` resolves against.
Generation goes through the OpenAI SDK; editing does not, because Meta indexes
its multipart reference images as `image[0]`, `image[1]`, … and rejects the
`image[]` the SDK emits. `EditImage` writes that body itself and posts it
through the SDK client, keeping the shared auth, base URL, and transport.

Muse Image is agentic: it runs its own web and image search before rendering, so
a prompt naming a real place or product is grounded with no tool configured.
That search is inside the per-image price and is not surfaced as tool calls.

**Muse Voice Transcribe** (`muse-voice-transcribe-1.0`, $0.18/hour of audio) is
a `media.TranscriptionProvider` over the file endpoint, `POST
/v1/asr/transcribe`. `WithTranscriptionMode` selects push-to-talk, endpointing,
or diarization; diarization's speaker labels and turn timestamps come back in
`TranscriptionResult.Metadata["turns"]`.

Two places where Meta differs from every other transcription provider Dive
speaks to, both of which would otherwise fail silently:

- `languageBias` takes a language *name*, not an ISO code, and answers a code
  with worse recognition rather than an error. `media.Config.Language` is mapped
  through the 25 supported languages, and anything unrecognized is passed
  through so a name — or a language Meta adds later — still reaches the API.
- There is no free-form prompt field; context is a keyword list. A caller's
  `TranscriptionPrompt` is refused with a message naming
  `WithTranscriptionKeywords`, rather than dropped.

The endpoint also accepts exactly one audio shape — RIFF/WAVE holding mono
16-bit PCM at 16 or 24 kHz — and answers everything else with a bare 400, so the
WAV header is parsed up front to name the specific mismatch and quote the
`ffmpeg` line that fixes it.

**Meta's realtime ASR** (`wss://api.meta.ai/v1/asr/realtime`) is not wired up.
It is a WebSocket with its own handshake, turn events, and pacing rules, none of
which `media.TranscriptionProvider` models. It needs a streaming interface
first, not an adapter.

## What was deliberately left out

- **Muse Glimmer**, the open-weight model. Self-hosted, served through vLLM or
  llama.cpp, so it reaches Dive through the Ollama / OpenAI-compatible path
  already, not through this provider.
- **Tool search.** `web_search` grounding is built ([above](#search-grounding));
  tool search — the server-side retrieval of tool definitions — is not.
- **`previous_response_id` chaining.** Dive's session model is stateless replay,
  and `llm.Config.PreviousResponseID` already exists for callers who want the
  server-managed form.
- **The Messages-format endpoint.** `POST /v1/messages` would let Dive's
  Anthropic provider talk to Muse Spark, which is a curiosity rather than a need
  given Responses is the richer surface.

## Open questions and risks

1. **The docs are one day old and visibly still in edit.** The published pricing
   page carries an unresolved editorial note — "Confirm these rate-limit numbers
   against the launch configuration before publishing. They are present in the
   current mdoc draft but are not specified in Part A of the positioning SoT."
   Prices and rate limits should be re-checked before this ships in a release.

2. ~~**No reasoning effort means no reasoning replay.**~~ Fixed: the include is
   now requested whenever the model reasons. See
   [Fixes upstream of this provider](#fixes-upstream-of-this-provider).

3. **Effort ladder is from documentation, not probe.** Every other entry in
   `modelcaps` was verified by sending the parameter to the live endpoint and
   recording 200 vs 400 — that is the package's stated contract. The Muse entries
   are read from Meta's docs. They should be probed before release, and the
   `minimal` end is the one to check first.

4. **`max_tokens` covers reasoning plus visible output.** The default of 32,768
   is inherited from Grok. On a model that can spend heavily on reasoning at
   `xhigh`, that may truncate visible answers. Worth a look once there is a key.

5. ~~**1M context vs. Dive's compaction defaults.**~~ Fixed: the CLI's threshold
   now scales to the model's usable context window. See
   [Compaction and the 1M window](#compaction-and-the-1m-window).

suite lives in `providers/meta/integration_test.go` behind the `integration`
build tag and skips when no key is set:

    MODEL_API_KEY=... go test -tags integration ./providers/meta/...

| Check | Result |
| --- | --- |
| `go build ./...` (root, `providers/meta`, CLI) | pass |
| `go vet ./...` | pass |
| `go test ./...` (root + `providers/meta`) | pass |
| `generate_provider_catalogs.py --check` | clean |
| `sync_module_versions.py --check v1.27.0` | clean |
| CLI lists Meta and `muse-spark-1.3` | pass |
| `GET /v1/models` returns all five catalogued ids | pass |
| Generation | pass |
| Streaming | pass |
| Usage reporting (`input`/`output` tokens) | pass |
| Tool calling | pass |
| **Encrypted-reasoning replay across a tool turn** | **pass** |
| Effort ladder `minimal`…`xhigh` accepted | pass, all five probed |
| Search grounding runs and returns its hits | pass, 2 calls and 10 sources |
| Image generation | pass |
| Image editing with reference images | pass |
| Transcription, push-to-talk | pass |
| Transcription, diarization | pass, two speakers labelled with turn timestamps |
| `provider_watch.py audit --provider meta` against the merged baseline | no changes |

The CLI's own `dive image` path against Muse Image is covered by a media
registry routing test rather than a live run: `getDefaultImageModel` checks Meta
last, so on a machine with `OPENAI_API_KEY` set an unqualified `dive image`
correctly picks OpenAI, and the routing test is what pins the model id to this
provider.

`GET /v1/models` returns exactly the seven ids the catalog now lists: five Muse
Spark, plus `muse-image-1.0` and `muse-voice-transcribe-1.0`. The
reasoning-replay test is the one that mattered: the first turn came
back with a `get_weather` tool call **and** a reasoning item carrying
`encrypted_content`, that item survived a JSON round trip the way a stored
session would, and Meta accepted it on replay alongside the tool result. That is
the behavior Chat Completions cannot provide, and it is now observed rather than
assumed.

Two things the live run taught that the docs did not:

- **Reasoning dominates the token bill on short prompts.** "Name one primary
  color" cost 12 input tokens and **425 output tokens** — roughly 420 of them
  invisible reasoning, billed at the output rate. Muse Spark reasons even with
  no effort set, so cheap-looking prompts are not cheap, and the default
  `max_tokens` of 32,768 is sized for reasoning plus answer for good reason.
- **Latency is substantial.** Trivial single-turn prompts took 14–67 seconds,
  and the five-effort ladder took 81 seconds for five one-word answers. Callers
  should expect the reasoning pause before first visible content that the docs
  warn about, and integration test timeouts need to be generous.

## Remaining open items

1. **Meta's pricing page is still visibly in edit** — it carries an unresolved
   editorial note telling its own authors to confirm the rate-limit numbers
   before publishing. Prices and limits should be re-checked before a release.
   This is the one risk a green test cannot close, which is what the provider
   watch entry is for.
2. **The effort ladder is read from documentation and confirmed by probe, but
   `none` was confirmed only as a 400.** That matches Meta's docs. If Meta later
   accepts `none`, `modelcaps` will clamp a legitimate value; the watcher sees
   catalog and pricing drift, not parameter drift.
3. **Realtime ASR** needs a streaming transcription interface in `media` before
   Meta's WebSocket endpoint can be wired up.
4. **Live search snippets came back empty** at `search_context_size: "low"`.
   Titles and URLs were populated. Worth a look at `medium` and `high` before
   documenting `IncludeResults` as a way to read what the model saw.
