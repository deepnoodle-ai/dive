**Mobius has built a durable execution runtime around Dive. The biggest opportunity is for Dive to expose execution as a sequence of acknowledged, recoverable steps—while letting Mobius own the transactions that make those steps durable.**

Dive already handles substantial complexity: provider differences, streaming, tool execution, hooks, and suspension. What makes this integration expensive is reconstructing the execution facts needed for recovery, accounting, and presentation after `CreateResponse` stops being one uninterrupted function call.

I reviewed Mobius at `5645a5b5a`, its pinned Dive **1.31.0**, and the newer sibling Dive implementation. That distinction matters: **Dive 1.34 already adds incomplete-turn outcomes, recoverable turn records, optional step checkpoints, and session claims.** Some gaps below are therefore adoption work; others remain questions about the integration boundary. [Dive 1.34 release](https://github.com/deepnoodle-ai/dive/releases/tag/v1.34.0)

**How the integration works today**

Mobius manages history itself and calls Dive with messages and callbacks. Its database, rather than a Dive session, owns the conversation and execution lifecycle. [Response construction](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent.go:2067)

| Concern | What Mobius provides |
|---|---|
| Execution ownership | Durable turn queue, claims, heartbeats, lease recovery, cancellation, and per-session serialization. |
| Conversation persistence | Incremental transcript commits, duplicate suppression, and an atomic final transcript/turn-status transaction. |
| Suspension | Storage of Dive’s suspension snapshot plus Mobius budgets, attachment references, and runtime constraints. |
| Resumption | Durable waits, result delivery, requeueing, ownership validation, reconstruction of the agent, and `WithResume`. |
| Failed execution | Error classification, partial-output salvage, transcript repair, and terminal settlement. |
| Accounting and presentation | Usage tracking across segments, billing identities, live previews, replayable events, and preview-to-persisted-message reconciliation. |

These are substantive abstractions, not thin adapters. The main executor alone is about 4,500 lines, with another 1,250 in resume handling. That size includes product behavior, but a significant portion is reconstructing and reconciling Dive execution.

There are good foundations here. The [durable substrate](/Users/curtis/git/deepnoodle/mobius-cloud/internal/durable) keeps reusable lease and wait mechanisms separate from domain policy. [Final settlement](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent.go:2697) commits transcript rows, input acknowledgements, and completion together. [Resume scheduling](/Users/curtis/git/deepnoodle/mobius-cloud/internal/daemon/session_runtime.go:1000) queues the continuation before retiring its wait.

**What makes this hard**

**1. A conversation record cannot establish whether an external effect happened.**

Consider this sequence:

1. Dive requests a tool.
2. Mobius dispatches its job.
3. The external service performs the action.
4. The process dies before the result reaches the transcript.

The tool call has an unknown outcome. Repeating it might duplicate the action; marking it failed might mislead the next model into repeating it.

Mobius already derives [job idempotency keys from tool-call identity](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/job_action.go:259). That protects repeated dispatch of the same identity. It cannot, by itself, protect a newly generated call expressing the same intent, or establish what an external service did before a lost acknowledgement.

This is the hardest boundary. Dive can preserve identity and uncertainty; downstream services and Mobius must still supply idempotency or reconciliation.

**2. Several representations must remain consistent.**

There is model history, live streamed output, durable transcript content, turn status, suspension state, and billing evidence. They have different purposes and persistence requirements.

Mobius consequently tracks response indexes, tool-result batches, preview message IDs, commit watermarks, and live sequence numbers. It even [scans backward through suspension messages](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_resume.go:1081) to distinguish generated output from preceding input.

Dive knows those boundaries during execution. Making downstream applications infer them afterward creates fragile code.

**3. Recovery must preserve both truth and provider-valid history.**

Mobius [repairs tool-call/result ordering, duplicates, and dangling calls](/Users/curtis/git/deepnoodle/mobius-cloud/internal/services/session_transcript.go:183). It also [rehydrates typed tool-result content](/Users/curtis/git/deepnoodle/mobius-cloud/internal/services/session_transcript.go:664), because JSON round-tripping loses Go types expected by provider converters.

Those are distinct operations:

- Preserve what actually happened.
- Produce a valid conversation for the next model request.

A synthetic tool result can satisfy a provider’s protocol without establishing the real outcome. Currently, the [dangling-call replacement](/Users/curtis/git/deepnoodle/mobius-cloud/internal/services/session_transcript.go:455) says the call failed because no result was recorded. “Outcome unknown” would express the evidence more accurately.

**4. Errors carry several incompatible meanings.**

A bad tool argument should usually return to the model. A lost lease should stop execution. A failed checkpoint must block progression. A deadline should preserve partial output. A budget stop is expected policy enforcement.

In the pinned Dive version, those distinctions travel through Go errors, `ToolResult.IsError`, hook-specific behavior, context cancellation, and response status. Mobius must interpret them repeatedly.

The clearest example is [the suspension checkpoint hook](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent.go:4321): Mobius must wrap persistence failure in `HookAbortError`, because an ordinary hook error is logged and execution can still suspend. Partial resumes need a [separate checkpoint path](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_resume.go:545) because `OnSuspend` does not fire again.

**The abstractions Dive should provide**

I would prioritize these in order.

**1. An acknowledged execution-record interface**

Expose durable steps separately from display events. The engine should require acknowledgement at recovery boundaries before advancing.

A small conceptual API could look like this:

```go
// Proposed shape, not an existing public API.
type Recorder interface {
    Commit(context.Context, Step) (Receipt, error)
}
```

Each step needs stable turn, invocation, model-call, and tool-effect identities; a sequence/version; and enough information to reconstruct execution. A write failure must distinguish **definitely rejected** from **commit outcome unknown**.

Mobius’s implementation could atomically:

- Verify the current owner and lease attempt.
- Store the execution step and transcript projection.
- Acknowledge consumed input.
- Record usage evidence or enqueue billing work.
- Create the durable continuation when applicable.

The engine should preserve an observed result when its recording fails, so the host can reload and reconcile without rerunning the effect.

This adds write latency and a protocol that needs versioning. It should be optional for simple callers, with explicit guarantees when enabled.

**2. A canonical turn record and history projector**

Dive should own the reusable semantics of:

- Which messages are input versus generated output.
- Tool-call/result pairing and partial batches.
- Completed, pending, never-started, and unknown tool calls.
- Serialization round trips.
- Producing provider-valid replay history.

Mobius should choose whether partial text appears in its UI or subsequent context. It should not have to reconstruct Dive’s message boundaries or repair library-owned content types.

This would replace substantial portions of the preview accumulator, resume-tail extraction, and transcript normalization.

**3. Typed outcomes and explicit recovery actions**

A report should independently describe:

- Execution status and stop reason.
- Persistence status.
- Tool-effect certainty.
- Permitted next action: continue, supply results, reconcile, or stop.

Tool APIs also need to distinguish recoverable model-facing failure from fatal infrastructure failure. Mobius currently [converts action execution errors into tool-result errors](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_tools.go:479), which loses information the runtime could use.

Retry advice must be scoped. Dive’s existing transport retry boundary—before the first stream event—is useful. Retrying an entire resumed agent loop is a different operation. Mobius’s [configured resume retry loop](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_resume.go:334) retries from the original suspension without a typed determination that no subsequent effect occurred.

**4. A complete model-call record**

Every model call should expose its identity, requested and served model, stop reason, observed usage, and whether usage is unknown. Those records should survive failure and resume.

Mobius currently builds [a concurrent cost meter](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_budget_meter.go:35), reconstructs usage from `GenerationError`, and invents billing identities such as `final`, `error:N`, and `suspend:<tool-call-id>`. [Segment accounting](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_model.go:170)

Dive should supply stable accounting facts. Pricing, customer credits, spending limits, and ledger transactions belong in Mobius.

**5. Reference-aware content serialization**

Mobius [removes attachment bytes from suspension JSON and restores them before decoding](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_resume.go:942). This avoids repeatedly storing large payloads and rechecks access on resume.

Dive would benefit from typed content references and a resolver boundary. Mobius would continue to own storage, authorization, retention, and the decision to release bytes.

A reasonable package separation would be:

```text
dive/execution  — steps, outcomes, recording, continuation
dive/history    — canonical content and replay projection
dive/session    — convenient persistence built on those contracts
```

**What should remain in Mobius—and what needs attention here**

Tenant authorization, connection grants, queues, lease policy, routines, retention, customer billing, and SSE delivery remain application responsibilities.

I also found three concrete gaps that better Dive contracts would help address, but would not automatically fix:

- **Ownership checks are uneven.** Dispatcher recovery uses holder/attempt checks, but ordinary executor checkpoint and completion writes use status predicates. An old executor can encounter a still-running turn owned by a newer attempt; status alone does not reject that owner. Cancellation-independent salvage writes make consistent ownership validation particularly important. [Checkpoint/completion predicates](/Users/curtis/git/deepnoodle/mobius-cloud/internal/adapters/postgres/agent_turn_repo.go:583)
- **Billing is outside final settlement.** Final usage recording happens after the completion transaction, and the usage recorder returns on billing failure. A crash between those operations leaves a recovery gap. Durable usage evidence or a transactional outbox would close it without making billing availability block the answer. [Usage recorder](/Users/curtis/git/deepnoodle/mobius-cloud/internal/agentruntime/executors/agent_model.go:200)
- **Suspension and wait creation are separate writes.** Mobius checkpoints `waiting`, then the dispatcher creates the wait. The orphan reaper prevents indefinite waiting, but its recovery is failure rather than restoration of the missing continuation. [Wait creation](/Users/curtis/git/deepnoodle/mobius-cloud/internal/daemon/session_runtime.go:563)

These are source-level findings, not reproduced production incidents.

**The next step I recommend**

Use one real Mobius flow to validate Dive’s existing [v2 prototype](/Users/curtis/git/deepnoodle/dive/experimental/v2/README.md): a turn that executes a job, suspends, resumes on another owner, and records usage. Exercise lost acknowledgements and process death between external execution and result recording. The prototype’s acknowledged steps and explicit uncertainty are closely aligned with this integration’s needs.

Separately, evaluate upgrading to 1.34 with explicit outcome mapping. It is not a dependency-only change: Mobius currently treats every non-suspended response reaching `handleTurnResponse` as a completion, while 1.34 can return an incomplete response with no Go error.

Focused tests covering suspension/resume, lease recovery, time budgets, and transcript repair passed across four packages. No files were changed; live-provider and process-crash behavior were not tested.
