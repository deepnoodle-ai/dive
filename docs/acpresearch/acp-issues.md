Issue status below means GitHub state at that time; an open report is not proof that every current version reproduces it. Source snapshots: [protocol `128845f`](https://github.com/agentclientprotocol/agent-client-protocol/tree/128845f5bd4c7fca5f23374e9b4853e470ecf99a), [Claude adapter `e6681d2`](https://github.com/agentclientprotocol/claude-agent-acp/tree/e6681d2a5734857727352474c8c9aa848f9210ee), [Go SDK `0845a3b`](https://github.com/coder/acp-go-sdk/tree/0845a3bb9eddda5bfc22a94dd3598c90cb842451), [Codex adapter `296069e`](https://github.com/zed-industries/codex-acp/tree/296069e841634cd4bb9bc4515602d836e49231ec), and [Gemini CLI `2fe7c2d`](https://github.com/google-gemini/gemini-cli/tree/2fe7c2d3f065dc40ad573d50b2091116f8a4aa18).

## Version boundary

The latest published **v1 schema** inspected was [`schema-v1.23.0`](https://github.com/agentclientprotocol/agent-client-protocol/releases/tag/schema-v1.23.0); the latest **v2 schema** was [`schema-v2.0.0-alpha.5`](https://github.com/agentclientprotocol/agent-client-protocol/releases/tag/schema-v2.0.0-alpha.5), both released September 18. The [v2 migration guide](https://github.com/agentclientprotocol/agent-client-protocol/blob/128845f5bd4c7fca5f23374e9b4853e470ecf99a/docs/protocol/v2/migration.mdx#L15-L28) calls the baseline schema stable *within v2* while labeling the overall v2 surface draft and recommending version negotiation and feature flags. Thus v2 documentation is a target contract, not evidence that today's agents negotiate v2.

The inspected [Codex adapter explicitly returns `ProtocolVersion::V1`](https://github.com/zed-industries/codex-acp/blob/296069e841634cd4bb9bc4515602d836e49231ec/src/codex_agent.rs#L440-L474). [Claude's adapter advertises v1-shaped `loadSession` and `sessionCapabilities`](https://github.com/agentclientprotocol/claude-agent-acp/blob/e6681d2a5734857727352474c8c9aa848f9210ee/src/acp-agent.ts#L2335-L2365). [Gemini CLI's native ACP dispatcher](https://github.com/google-gemini/gemini-cli/blob/2fe7c2d3f065dc40ad573d50b2091116f8a4aa18/packages/cli/src/acp/acpRpcDispatcher.ts#L81-L104) likewise advertises `loadSession`; it implements `loadSession` but has no `resumeSession` handler in that dispatcher ([source](https://github.com/google-gemini/gemini-cli/blob/2fe7c2d3f065dc40ad573d50b2091116f8a4aa18/packages/cli/src/acp/acpRpcDispatcher.ts#L177-L187)).

Claude adapter [#864](https://github.com/agentclientprotocol/claude-agent-acp/issues/864) and [#876](https://github.com/agentclientprotocol/claude-agent-acp/issues/876) remain open for background-shell output or user-input requests after the prompt settles. [#976 remains open](https://github.com/agentclientprotocol/claude-agent-acp/issues/976); a September 26 comment reports it still reproduces on adapter 0.81.2 in Zed. | A durable session controller should track session activity separately from the foreground turn and continue accepting connection-scoped permission requests. ## Closed, changed, or narrower than the title suggests

- **v1 update vocabulary:** [#1694 was closed by merged documentation PR #2214](https://github.com/agentclientprotocol/agent-client-protocol/pull/2214) on September 23. The v1 schema had 11 standard `SessionUpdate` variants while the former prose page listed five; the PR adds variant tables and says updates may occur outside prompt processing. This was a documentation fix, not a wire change. Clients still need a tolerant dispatcher for future/custom variants.
- **Claude replayed approvals:** [#1094 is closed by its reporter](https://github.com/agentclientprotocol/claude-agent-acp/issues/1094). Same-`toolCallId` history replay after `session/load` was observed, but the reporter's later tests did **not** demonstrate a stale approval authorizing a new filesystem effect. Do not repeat the original title as a proven authorization defect. The question of cross-restart approval semantics remains separate.
- **Go SDK session support:** [Go issue #14 is still open](https://github.com/coder/acp-go-sdk/issues/14), but its January 2026 claim that Go lacks resume/list/fork is stale. Current generated code includes [session capability fields](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/types_gen.go#L4420-L4451) and [`ResumeSession`, `ListSessions`, and unstable `ForkSession`](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/client_gen.go#L271-L303); releases describe [stable resume in v0.12.2](https://github.com/coder/acp-go-sdk/releases/tag/v0.12.2). `session/load` remains separately available. Read the current generated API, not that issue's opening body.
- **Go ordering repairs:** SDK [#20](https://github.com/coder/acp-go-sdk/issues/20) and [#27](https://github.com/coder/acp-go-sdk/issues/27) are closed. Merged [PR #8](https://github.com/coder/acp-go-sdk/pull/8) serializes notification processing; [PR #30](https://github.com/coder/acp-go-sdk/pull/30) adds a response-scoped barrier that waits for notifications accepted *before* a response, not later ones. The current code has a [single notification queue and sequence watermark](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection.go#L80-L125). This repairs the SDK's earlier reorder bug but does not settle protocol issue #554 for post-response notifications.
- **Go remaining concurrency risks:** [#57](https://github.com/coder/acp-go-sdk/issues/57) and duplicate [#58](https://github.com/coder/acp-go-sdk/issues/58) remain open; current `SetLogger` writes a field after the constructor starts reader/worker goroutines, with no synchronization ([source](https://github.com/coder/acp-go-sdk/blob/0845a3bb9eddda5bfc22a94dd3598c90cb842451/connection.go#L91-L132)). [PR #56](https://github.com/coder/acp-go-sdk/pull/56) is also open to order inbound requests after earlier notifications. The last Go SDK release inspected was [`v0.13.5`, June 2](https://github.com/coder/acp-go-sdk/releases/tag/v0.13.5); it predates the current v1 schema release.

## Resume and remote transport boundary

In v1, `session/load` restores context **and** replays history, while `session/resume` restores context **without** replay when advertised. The protocol maintainer confirmed that clients can fall back to `loadSession` and ignore replay if an agent lacks `sessionCapabilities.resume` ([#1378, closed](https://github.com/agentclientprotocol/agent-client-protocol/issues/1378)). Current adapters make the difference concrete: [Claude has separate methods](https://github.com/agentclientprotocol/claude-agent-acp/blob/e6681d2a5734857727352474c8c9aa848f9210ee/src/acp-agent.ts#L2415-L2445); [Codex calls one restore function with `replay_history` true/false](https://github.com/zed-industries/codex-acp/blob/296069e841634cd4bb9bc4515602d836e49231ec/src/codex_agent.rs#L608-L672); [Gemini implements `load` from persisted session data and streams history](https://github.com/google-gemini/gemini-cli/blob/2fe7c2d3f065dc40ad573d50b2091116f8a4aa18/packages/cli/src/acp/acpSessionManager.ts#L166-L216). A browser-bridge issue [#1104](https://github.com/agentclientprotocol/agent-client-protocol/issues/1104) reports a successful restart using `load`; its title mentions `resume`, but the reporter explicitly says that particular test did not call it.

The v2 draft [removes `session/load`](https://github.com/agentclientprotocol/agent-client-protocol/blob/128845f5bd4c7fca5f23374e9b4853e470ecf99a/docs/protocol/v2/migration.mdx#L574-L604). `session/resume` becomes a required baseline method; omit `replayFrom` for no replay, or use `{ "type": "start" }` for full retained-history replay. Its [replay cursor is inclusive and the agent must finish requested replay before responding](https://github.com/agentclientprotocol/agent-client-protocol/blob/128845f5bd4c7fca5f23374e9b4853e470ecf99a/docs/protocol/v2/session-setup.mdx#L118-L222). That is a **conversation replay cursor**, not yet a durable remote event-stream cursor.

For transport, both v1 and v2 currently define **stdio**; the [v2 transport page still labels Streamable HTTP draft](https://github.com/agentclientprotocol/agent-client-protocol/blob/128845f5bd4c7fca5f23374e9b4853e470ecf99a/docs/protocol/v2/transports.mdx#L6-L15). The merged [HTTP/WebSocket RFD](https://github.com/agentclientprotocol/agent-client-protocol/blob/128845f5bd4c7fca5f23374e9b4853e470ecf99a/docs/rfds/streamable-http-websocket-transport.mdx#L64-L85) expressly leaves v1 reconnect/retry to implementers and offers **no replay of in-flight messages missed during a disconnect**. A follow-on [durable/resumable HTTP/WS RFD PR #2208](https://github.com/agentclientprotocol/agent-client-protocol/pull/2208) is open as of this check. Therefore an Nvoken-style cursor and durable event log would add a real guarantee for remote sessions beyond today's standard ACP transport, while an ACP adapter can still expose local stdio interoperability.

## Practical research takeaways

1. For a Dive **agent adapter**, target negotiated v1 first and emit a complete ordered `session/update` stream. Publish a tool call before a permission request that references it. Keep public session IDs mapped to actual persisted runtime history. Use capability flags for list/load/resume/fork rather than assuming uniform support.
2. For a Dive or Nvoken **ACP client**, parse all standard update variants, tolerate future variants, keep permission handling connection scoped, and keep foreground-turn and background-session state separate. Preserve event order before building transcript text or tool-call state. Treat replayed tool calls as historical display, never a fresh command to execute.
3. For **remote control**, run ACP behind a bridge only with an explicit durability contract: who owns the process, how session IDs survive restart, how missed notifications are recovered, and what approval state means after reconnect. ACP v2's `replayFrom` helps rebuild a retained conversation; it does not yet specify live stream resumption or effect-bound approvals.

These are implementation recommendations inferred from the cited protocol and issue evidence, not behavior validated against Dive. No live agent interoperability test was run for this research pass.
